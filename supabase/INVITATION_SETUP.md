# 招待制の新規登録の管理

公開リポジトリ、フロントエンド、`VITE_*`、GitHub Actions のビルド変数に正解の招待コードを入れないでください。ビルド変数を非公開にしても、Vite がブラウザー用 JavaScript に埋め込めば閲覧できます。

## 別環境への適用・再設定

1. Supabase Dashboard の Vault に、名前 `limenote_signup_invite_code` の secret を作成します。値には管理者が決めた招待コードを入力します。実際のコードはこの文書には記載しません。
2. SQL Editor で `migrations/20261001120000_require_signup_invitation.sql` を実行します。既存プロジェクトには他のマイグレーション履歴がないため、このファイルだけを適用する方法が確実です。CLI の migration 管理を既に使っている場合は通常の手順で適用できます。
3. 更新したフロントエンドを公開します。
4. 招待コードなし・不正なコードで新規登録が失敗し、正しいコードのみで登録できることを確認します。既存アカウントのログインも確認します。

Vault の値を先に登録しても、SQL を適用するまでは登録制限は有効になりません。SQL 適用後は、古いフロントエンドからの登録は拒否されます。秘密が未設定・空でも登録は拒否されます。

## 制限の仕組み

Auth の `auth.users` に対する INSERT をデータベースのトリガーで制限します。画面やクライアント検証を回避した直接の Auth API 呼び出しでも、正しいコードなしではユーザー行を作成できません。管理画面・OAuth・管理 API を含め、新しいユーザーを作る経路にも同じ制限が適用されます。既存ユーザーのログイン・更新には招待コードを要求しません。

秘密を読む関数は専用の `limenote_auth_private` スキーマにあります。提出された値は登録時のみ照合し、保存前に `raw_user_meta_data` から削除します。Vault を読む関数は非公開スキーマ内に配置し、ブラウザーの anon/authenticated ロールから実行できなくしています。

招待コードの変更は Vault 内で値を更新します。再ビルドは不要です。固定の共通コードなので、知っている人は何度でも登録できます。

## 確認用 SQL

`tests/signup_invitation.sql` はトランザクション内でテスト用の値を設定し、仮の Auth ユーザーテーブルで未設定・不正・正しいコードとメタデータ除去を確認します。最後に ROLLBACK し、実際のユーザーや Vault の値を変更しません。SQL Editor では全体を一度に実行してください。
